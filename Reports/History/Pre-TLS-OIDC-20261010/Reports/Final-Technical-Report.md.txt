# SECX-001 Technical Report

Review date: 2026-10-10. Status: **In progress - current evidence review**. The filename is the project's consolidated technical report; it does not mark the project complete or authorize publication.

## Objective and Business Impact

Protect an internal training application's access path, add application authentication, and verify that a controlled service restart restores the authentication endpoint. In a business setting, these controls can reduce unnecessary workload exposure and unauthorized content access while supporting service recovery. This isolated lab demonstrates the tested behavior; no production deployment, financial savings, uptime SLA or enterprise certification is claimed.

The most useful evidence is the sequence: unrestricted baseline, restrictive UFW policy, approved-path access, non-approved client denial, credential rejection/success, controlled outage, restart and remote negative retests. Those stages explain the purpose of each control rather than treating every HTTP response as equivalent.

## Environment and Architecture

Ubuntu serves the application at 10.10.10.101:8080 through secx001-app.service. The earlier service used Python SimpleHTTP; the authentication deployment points ExecStart to auth_server.py. UFW permits the configured Kali source 10.10.10.100 on enp0s8 and administrative SSH on enp0s3. The Windows negative test identifies source 10.10.10.1. OV-DC01 at 10.10.10.10 is used for separate AD/DNS investigation.

The [architecture diagram](../Architecture/Architecture.md) is an evidence-based logical reconstruction. It is not an exported hypervisor configuration. The allowed Kali IP is visible in the UFW rule, while a dedicated Kali source-address inventory capture is still missing. The administrative SSH alias configuration is also missing.

## Threat Model and Trust Boundaries

| Scenario | Boundary / Control | Observed Mitigation | Remaining Risk |
| --- | --- | --- | --- |
| Unapproved client probes the app | Ubuntu host firewall | Windows TCP 8080 test fails; earlier UFW events show matching blocks | Current full rules/export, IPv6 and other paths not comprehensively tested |
| Approved-path client has no credentials | Application HTTP Basic | Ubuntu 401 and post-recovery Kali 401 | Plaintext transport exposes any subsequently supplied credentials |
| Approved-path client submits invalid credentials | Application credential check | Kali 401 before and after restart | Rate limiting, lockout and brute-force handling not evidenced |
| Approved-path client has valid credentials | Local application account | Ubuntu/Kali Python requests return 200; content check true | No enterprise identity, device assurance, role separation or credential lifecycle demonstrated |
| Service becomes unavailable | systemd restart and socket/HTTP validation | Controlled stop removes listener; restart restores listener and 401 challenge | Valid-credential post-recovery access and recovery timing not verified |
| DNS resolves unexpectedly | DNS dependency and investigation | DC/GC names resolve; domain-root A answer is empty in latest detailed query | DNS-001 remains open pending intended record policy and validation |

The network boundary and application boundary are independent. A 401 proves that an HTTP authentication endpoint answered a reachable request. A blocked TCP connection prevents reaching that endpoint. Neither is proof of complete enterprise Zero Trust.

## Security Controls

- Host-based microsegmentation: incoming UFW default deny with a source-, interface- and port-specific application allow.
- Administrative path: SSH permitted on the NAT-facing interface, including IPv6, from Anywhere on that interface. This is not a source-restricted administrative rule.
- Application authentication: HTTP Basic with a local application account. Valid password entry uses getpass in the successful Python tests.
- Operational control: systemd service state, enablement and listener checks; controlled stop/start exercise.
- Monitoring: UFW block events correlated by source, destination, port and interface; application journal includes request status.
- Recovery preparation: existing DNS snapshot and export evidence, separate from service restart validation.

HTTP Basic without TLS remains a material security limitation: Basic encoding does not encrypt credentials, and content is also unencrypted. The authentication implementation and configuration were not exported or inspected, so password storage and comparison behavior are not certified by these tests.
